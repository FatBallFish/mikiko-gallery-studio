# Backend P0 Gap Fill Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Fill the backend P0 gaps listed in `docs/plans/2026-05-22-backend-feature-gap-and-frontend-api-handoff.md`, in priority order, and update that handoff document after implementation.

**Architecture:** Keep the existing Go monolith shape: HTTP handlers in `internal/http/handlers`, routing in `internal/http/router`, domain/service/store boundaries under `internal/domain`, `internal/service`, and `internal/repository/entstore`. Prefer small read/write services over growing `api.go` with persistence logic; reuse existing Ent schemas unless a gap truly requires schema expansion. The implementation must preserve tenant scoping by `user_id`, admin-only access through `requireAdmin`, and consistent JSON envelopes through `pkg/httpx`.

**Tech Stack:** Go, net/http ServeMux, Ent, SQLite/PostgreSQL-compatible Ent tests, OpenAPI 3.1 YAML, repository workflow scripts.

## Task 1: Generated Image Result Persistence And Download

**Goal:** Make generated image results durable and retrievable by frontend.

**Files:**
- Modify: `internal/domain/imagetask/types.go`
- Modify: `internal/provider/contracts.go` only if needed for API result metadata; prefer avoiding provider pollution.
- Modify: `internal/service/assets/service.go`
- Modify: `internal/service/assets/store.go` if a result lookup interface belongs there.
- Modify: `internal/service/imagetask/store.go`
- Modify: `internal/repository/entstore/imagetask_store.go`
- Modify: `internal/http/handlers/api.go`
- Test: `internal/repository/entstore/imagetask_store_test.go`
- Test: `internal/http/router/tasks_api_test.go`
- Update if needed: `api/openapi/components/schemas/common.yaml`, `api/openapi/openapi.yaml`

**Acceptance Criteria:**
- Succeeded tasks persist real `task_images` metadata, not placeholder-only metadata.
- For `b64_json` provider results, bytes are decoded, stored under local generated image storage, and `task_images` records include `object_key`, `mime_type`, `file_size_bytes`, `width`, `height`, and `sha256`.
- For remote URL provider results, P0 may store remote metadata and return original URL in task response, but the implementation must clearly support frontend rendering. If bytes are not fetched in P0, document that in code/tests and handoff.
- Task detail/history responses expose usable result objects with at least `id`, `url` or `download_url`, `mime_type`, `width`, `height`, `file_size_bytes`, `visibility_status`.
- `GET /api/agent/image/v1/images/{image_id}` serves local generated bytes for the owner and returns not found for non-owner or deleted results.
- Deleting a history task also hides generated image results from the download endpoint.

**Test Commands:**
- `go test ./internal/repository/entstore -run 'ImageTask|ImageResult' -count=1`
- `go test ./internal/http/router -run 'AgentTask|ImageDownload' -count=1`

**Status 2026-05-22:** Completed. Local `b64_json` generated results are persisted to generated storage and `task_images`; remote URL results are persisted/returned as URLs but not mirrored locally in this pass.
