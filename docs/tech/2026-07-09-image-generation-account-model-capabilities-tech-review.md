## 一、评审结论

**Gate 判定**：通过

**一句话总结**：方案整体方向正确，采用“账号真实模型维度的一等能力字段 + capabilities 能力并集 + Resolver 统一完整组合匹配 + Worker 双模式参数转换”的路径，符合当前项目模型路由架构，也符合业界按模型/端点暴露参数能力的主流做法；初审发现的兼容和匹配语义问题已修正，当前可准出进入实现。

## 二、方案复述还原

### 一句话摘要

本方案把图片生成模型能力从前端硬编码和零散配置中收敛到 `model_account_models`，再由后端统一聚合、校验、预估和执行，支持比例模式与像素模式两条清晰链路。

### 核心架构决策

| 决策点 | 方案选择 | 评审判断 |
|---|---|---|
| 能力存储维度 | 存在账号下真实模型 `model_account_models` | 正确，符合 PRD 中“同账号不同模型能力不同”的约束 |
| 存储方式 | 一等字段优先，`extra` 仅迁移兜底 | 正确，避免核心业务契约沉入弱类型 JSON |
| 能力展示 | capabilities 返回路由模型下候选能力并集 | 正确，但必须配合 estimate 完整组合校验 |
| 支持性判断 | estimate/create/Worker 均走 Resolver 统一匹配 | 正确，是防止前端可选但执行失败的关键 |
| 像素模式计费 | 像素尺寸映射到 `1k/2k/4k` 质量桶 | 可接受，需产品确认定价语义 |

### 系统交互全景

管理后台写入账号真实模型能力配置；用户端通过 capabilities 获取可见路由模型的能力集合；用户选择参数后，estimate 先用 Resolver 找到完整支持该组合的候选，再由 Billing 计算积分；创建任务重复执行同一匹配；Worker 租约任务后再次按任务参数筛选候选，并根据 `size_mode` 构造上游请求。

### 方案边界

- **In-scope**：Admin 能力配置、capabilities 聚合、estimate/create 校验、Worker ratio/pixel 执行、Codex 尺寸诊断、灰度与测试。
- **Out-of-scope**：新增上游账号类型、大规模重构路由策略、重构积分体系、扩充大量默认像素尺寸、非图片生成模块。
- **外部依赖**：OpenAI/Codex/Adobe 等上游接口真实尺寸支持情况，仍需通过后台测试入口和日志确认。

### 复述中发现的疑问

初审发现以下疑问，均已在方案中修正或标为人工确认：

- 【缺失】estimate 原方案没有明确先 Resolver 再 Billing，可能导致 estimate 与 create task 支持性判断不一致。已补 `EstimateResolved` 编排契约。
- 【歧义】`max_reference_image_count=0` 是默认缺省还是不支持参考图。已明确 0 是合法值，表示不支持参考图。
- 【缺失】旧客户端会提交 `requested_size` 而不是 `aspect_ratio`，原方案未钉死兼容路径。已补内部 `legacy_ratio_size` 契约。
- 【歧义】像素模式是否还受候选 `qualities` 约束。已明确像素模式推断质量桶后仍需满足候选显式质量限制。

## 三、全局架构审视

### 问题域与业界做法

行业实践上，图片生成接口普遍把 `size`、`quality`、输出格式、参考图能力等参数作为模型或端点级能力约束。模型聚合类平台也倾向于通过模型元数据描述支持参数，再由调用方按模型能力构造请求。因此，平台内部维护归一化能力矩阵，并由后端统一做参数匹配，是合理方向。

### 方案整体评估

方案与当前项目已有模型路由改造自然衔接，没有引入新服务或新的路由范式。关键风险不是架构方向，而是“capabilities 并集容易让用户选到无候选支持的组合”。修订后方案已明确 estimate/create/Worker 都必须使用同一个候选匹配器，并要求前端每次参数变化后重新 estimate，因此该风险已被控制。

### 全局判定

方向正确。剩余待确认项主要是产品定价、默认像素尺寸、灰度开关等人工决策，不阻塞技术方案准出。

### 数据模型

数据模型符合项目现状：项目使用 Ent + PostgreSQL，已有 `task_types/qualities` JSON 字段，新增 `size_modes/supported_ratios/supported_pixel_sizes` 与既有风格一致。新增列均为加法变更并带默认值；`image_tasks.size_mode` 不新增索引的判断合理。

已修正关键语义：`max_reference_image_count=0` 不做默认补齐，表示不支持参考图。

### 项目现状验证

已对照代码确认：

- `model_account_models` 当前已有 `task_types/qualities/extra`，适合扩展一等字段。
- `modelhub.ProviderCandidate` 已承载任务类型、质量、比例、数量等能力，是新增 `SizeModes/SupportedPixelSizes` 的自然位置。
- 当前 `billing.Calculator` 只做质量/点数计算，初版方案缺少 estimate 支持性匹配编排，已补正。
- 当前用户端会在前端将比例+清晰度计算成 `requested_size`，已补旧客户端兼容和新客户端迁移契约。
