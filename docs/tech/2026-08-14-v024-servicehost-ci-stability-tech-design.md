# v0.0.24 ServiceHost CI 稳定性修复技术方案

## 现状分析

ServiceHost 测试使用真实测试二进制作为子进程，以退出码 `75` 验证自动重启。现有测试先同步执行 `RunChild`，依赖 `120ms` 超时结束循环，之后读取计数文件。这把 Runner 调度耗时误当成了业务同步条件。

辅助子进程通过 `os.WriteFile` 直接更新计数文件。该调用会先截断文件；当 `exec.CommandContext` 因测试上下文超时杀死子进程时，可能留下空文件。远端失败日志中的 `restart count = ""` 与这一窗口一致。

## 设计

### 条件驱动的停止

- 在 goroutine 中运行 `RunChild`。
- 主测试轮询原子计数文件，直到观察到计数大于等于 2。
- 达成条件后主动取消上下文，并等待 `RunChild` 返回。
- 为轮询和退出分别设置有界超时，避免测试无限等待。

### 不可变重启标记

- 辅助子进程每次启动时在专用目录创建一个唯一 marker 文件，不再读写共享计数文件。
- 父测试只统计固定前缀的 marker 数量，不会读取到截断或部分覆盖的内容。
- 创建或关闭 marker 失败时让辅助进程以普通失败码退出，使测试暴露真实错误。

### 测试辅助函数

在 `runner_test.go` 内提供仅测试使用的 marker 统计逻辑，不扩展生产 API。

## 风险控制

- `RunChild` 仍由可取消上下文控制，生产实现不变。
- 轮询间隔保持较短，但使用 deadline 限定总时长。
- marker 文件只创建、不覆盖，且每次启动使用唯一名称，兼容各目标操作系统。

## 验证计划

1. 先增加测试辅助函数契约并观察其在实现前失败。
2. 运行目标用例 `-count=100`。
3. 在 Linux Go 容器中运行目标用例 `-count=100`。
4. 执行仓库 verify、committed review gate、ship guard 和 API smoke。
5. 合入 `main` 后发布 `v0.0.24`，监控完整 Tagged Release。
