## 1. 需求背景与目标

### 1.1 背景

当前图片生成能力主要以两类形态提供：

1. 底层模型 API：能力强但直接使用门槛高，计费、参数差异、密钥管理、历史图片管理、失败重试等应用层能力需要业务方自行封装。
2. 单一图片生成产品：面向终端用户体验较完整，但通常不支持多底层模型路由、统一积分结算、API 密钥分组、运营后台灵活调价和成本核算。

Pic Gallery 的定位介于 API 中转服务和独立图像生成应用之间：在 GPT、Gemini、OpenRouter、国内图像模型等底层 API 之上，封装用户体系、图床与历史记录、提示词优化预留、抽象模型分组、积分计费、套餐订阅、密钥管理、模型路由、图生图/参考图生成和超级管理员运营后台。

### 1.2 为什么现在做

- 生成式图片使用场景增长，但底层模型价格、稳定性和参数能力持续变化，单一模型接入会造成成本和可用性风险。
- 个人或小团队使用底层 API 时缺少统一的额度、历史图片、支付充值和 API Key 管理能力，影响转化和复购。
- 图生图、参考图生成和二次编辑已经是高频需求，如果 MVP 阶段只支持文生图，平台在真实场景中的可用性会明显不足。
- 管理端若不能动态配置模型分组、价格、优先级、生成参数上限和降级策略，每次调整都需要研发介入，运营成本高。
- 如果不在 MVP 阶段建立积分、会话安全、审计和历史数据闭环，后续补齐计费、登录安全和公开分享能力会产生迁移成本。

### 1.3 产品目标

| 目标 | 量化指标 |
|---|---|
| C 端用户可完成从注册、登录、充值/兑换、文生图/图生图到历史查看的完整闭环 | 首次访问到成功生成图片的核心路径不超过 7 步；图片生成成功后 3 秒内可在历史中看到记录 |
| Web 登录态可安全续期 | 用户登录后获得 Access Token + Refresh Token；Access Token 失效且 Refresh Token 有效时可静默续期，不打断当前页面操作 |
| API 开发者可通过 AK/SK 调用平台生图能力 | 用户可在 2 分钟内创建可用密钥；密钥可配置启停、过期时间、额度和限速 |
| 运营可在后台独立调整计费和模型调度 | 模型分组、单次积分消耗、生成数量上限、兑换码、用户额度调整不需要发版即可生效 |
| 平台可追踪收入、积分消耗和底层模型成本 | 每笔生成任务保留任务类型、积分扣减、底层模型、成本、状态、错误原因和操作人信息 |
| 平台具备后续公开分享能力 | 历史图片可申请公开并进入人工审核；P1 阶段审核通过后可在图片广场展示 |
| MVP 可容器化部署并支持后续扩展 | Docker 部署包含后端、用户 Web 前端、管理后台 Web 前端；支持单机与集群部署；目录和模块边界支持后续支付、提示词优化、更多模型扩展 |
| API 开发者可快速接入与调试 | 平台提供原生 API、OpenAI 兼容图片接口和开发文档页面；接口用途、出入参、示例代码可查可用 |

## 2. 用户故事与 JTBD

### 2.1 C 端图片生成用户

- 作为一名需要快速生成配图的内容创作者，当我有一段文字描述或已有一张基础图片但不想理解不同模型的复杂参数时，我希望选择 Basic/Plus/Pro 这类抽象模型，并完成文生图、二次编辑或参考图生成，从而快速得到可下载、可复用的图片。
- 情境：用户要为文章、营销素材、社媒封面、电商商品图生成图片，或者基于已有草图、旧图继续修改。
- Job：用最低学习成本把文字创意或已有图片转化为符合尺寸和质量要求的结果图。
- 期望结果：图片生成过程可预期，失败原因可理解，消耗积分透明，历史记录可找回。
- 现有替代方案：直接用底层模型网页或 API；问题是参数分散、价格不可控、历史管理弱。

### 2.2 API 开发者

- 作为一名需要在自己应用中集成生图能力的开发者，当我不想分别维护多个底层模型账号和计费逻辑时，我希望通过 Pic Gallery 的 API Key 调用统一接口，从而把模型差异、计费和失败降级交给平台处理。
- 情境：开发者要在业务应用、Bot 或自动化流程中调用文生图、图生图或参考图生成。
- Job：稳定、可控、可计费地集成图片生成能力。
- 期望结果：密钥权限和额度可控，请求状态可查询，失败有明确错误码，不会无限制消耗积分。
- 现有替代方案：直接接 OpenAI/OpenRouter/国内模型；问题是多模型兼容、费用核算和限流都要自建。

### 2.3 平台运营/超级管理员

- 作为平台运营管理员，当底层模型价格、质量或可用性变化时，我希望在后台配置抽象模型分组、优先级、AB 分流、降级策略、任务类型倍率和积分消耗，从而在不发版的情况下控制成本、稳定性和用户体验。
- 情境：某模型涨价、故障或质量下降，需要快速调整调用策略；或者产品需要临时调低生成数量上限、调整公开审核开关。
- Job：在成本、质量、稳定性之间做运营配置。
- 期望结果：配置生效范围清晰，可查看历史调用和成本，关键操作可审计。
- 现有替代方案：研发改配置或改代码；问题是响应慢、风险高、不可追溯。

### 2.4 图片分享用户

- 作为一名希望展示作品的用户，当我对生成结果满意时，我希望把历史图片申请公开，在管理员审核通过后进入图片广场，从而让其他用户看到平台生成效果。
- 情境：用户希望展示作品、提升曝光，或者给其他用户提供参考。
- Job：在不影响私有图库的前提下，把单张图片作为公开内容分享出去。
- 期望结果：公开操作简单、审核状态透明、被拒绝时原因可见。
- 现有替代方案：用户只能自行下载后发到外部平台；问题是平台内缺少分享沉淀和内容运营能力。

## 4. 角色与权限边界

| 角色 | 说明 | 关键权限 |
|---|---|---|
| 游客 | 未登录访问者 | 查看登录/注册页、查看产品介绍、查看公开图片广场，不可发起生成 |
| 注册用户 | 完成邮箱验证的普通用户 | 文生图、图生图、参考图生成、查看个人历史、管理个人资料、查看余额、兑换码兑换 |
| 付费/订阅用户 | 拥有有效套餐或余额的注册用户 | 使用套餐内额度、享受套餐绑定的抽象模型与限速 |
| API 开发者 | 使用 AK/SK 调用 API 的注册用户 | 创建和管理密钥、通过 API 发起生成任务、查询任务 |
| 超级管理员 | 独立管理员体系中的最高权限用户 | 管理用户、积分、兑换码、模型、调度、价格、监控、审核配置和审计 |
| 运营管理员 | 可选后台角色，本期可由超级管理员创建 | 查看运营数据、生成兑换码、调整活动配置、处理公开图片审核；不可改底层模型密钥 |
| 系统 | 平台自动执行者 | 计费、任务状态流转、模型路由、降级、Token 刷新、日志记录 |

### 4.1 分权分域

- 客户端用户只能访问自己的资料、密钥、积分流水、生成任务和图片；不得查看其他用户私有数据。
- 图片广场中的公开图片仅展示审核通过的内容；未通过或待审核图片不能被其他用户访问。
- 管理后台用户体系与客户端用户体系独立，管理员不能使用 C 端账号登录后台。
- 超级管理员可查看全量用户和调用数据，可调整用户积分、并发、RPM、账号状态和公开审核策略。
- 运营管理员默认不能查看底层模型密钥明文，不能修改管理员权限，不能删除审计日志。
- API Key 只能作用于所属用户；密钥分组、额度、过期时间和限速不能突破用户账号级限制。
- 所有后台写操作必须写入审计日志，审计日志不可由普通后台页面删除。

## 5. 核心对象与状态机

### 5.1 用户账号

| 状态 | 说明 | 触发 |
|---|---|---|
| 未注册 | 邮箱未入库 | 游客访问 |
| 待验证 | 邮箱提交后等待验证码验证 | 用户注册 |
| 正常 | 可登录并使用功能 | 验证通过/管理员启用 |
| 禁用 | 不能登录、不能生成、API Key 不可用 | 超级管理员禁用 |
| 注销预留 | 本期不开放自助注销 | 后续合规扩展 |

### 5.2 图片生成任务

| 状态 | 说明 | 触发/前置条件 | 后置动作 |
|---|---|---|---|
| 待校验 | 接收请求后参数尚未校验 | 用户提交文生图/图生图/参考图请求 | 校验参数、权限、余额、限速 |
| 已拒绝 | 参数、权限、余额或限速不满足 | 校验失败 | 返回明确错误，不扣除生成积分 |
| 排队中 | 通过校验，等待模型调度 | 余额满足且请求合法 | 锁定/预扣预计积分，写任务记录 |
| 生成中 | 已选择底层模型并调用 | 模型路由成功 | 等待同步响应或异步回调/轮询 |
| 成功 | 至少 1 张图片生成并保存成功 | 底层模型返回成功且图床保存成功 | 扣除实际积分，生成图片记录和流水 |
| 部分成功 | 多图请求中部分图片成功 | 部分底层调用失败 | 仅按成功图片扣费，展示失败明细 |
| 失败 | 未生成任何可用图片 | 底层模型失败且降级后仍失败 | 释放预扣积分或生成退款流水，展示错误原因 |
| 已删除 | 用户删除历史记录 | 用户主动删除 | 图片不再在用户图库展示，保留必要审计和计费流水 |

### 5.3 API Key

| 状态 | 说明 | 触发 |
|---|---|---|
| 启用 | 可调用 API | 用户创建/启用 |
| 禁用 | 不可调用 API | 用户或管理员禁用 |
| 已过期 | 超过过期时间 | 系统判定 |
| 已重置 | Secret 已轮换，旧 Secret 不可用 | 用户重置 |
| 已删除 | 不可恢复 | 用户删除 |

### 5.4 积分流水

| 生成扣减 | 任务成功或部分成功 | 按实际成功图片数量扣减 |
| 失败返还 | 任务预扣后失败 | 返还预扣积分 |
| 管理员调整 | 后台手动增减 | 必须填写原因并审计 |
| 过期扣减 | 套餐或活动积分到期 | 到期自动扣减并保留流水 |

| 状态 | 说明 |
|---|---|
| 未生效 | 到达生效时间前不可兑换 |

| 已过期 | 超过有效期 |

### 5.6 图片公开状态

| 状态 | 说明 | 触发 |

## 6. 用户操作流程

### 6.1 C 端图片生成主流程

1. 游客进入客户端首页，点击登录/注册。
2. 用户输入邮箱，获取验证码，完成注册或登录；登录成功后系统签发 Access Token 和 Refresh Token。
3. 用户进入图片生成页，查看当前余额、套餐、抽象模型可用范围和预计消耗说明。
4. 用户选择任务类型：文生图、二次编辑、参考图生成；后二者需上传参考图片。
5. 用户输入提示词，选择抽象模型（Basic/Plus/Pro）、质量（1K/2K/4K）、比例、数量和保存方式。
6. 系统实时展示预计积分消耗；余额不足时禁用提交并引导充值/兑换。
7. 用户提交生成请求。
8. 系统进行参数、权限、余额和限速校验；通过后创建生成任务。
9. 同步模式下页面展示等待态并在完成后展示图片；异步模式下页面展示任务卡片，用户可刷新或轮询查看结果。
10. 生成成功后，用户可预览、下载、复制图片链接、删除历史记录；P1 阶段可对单张历史图片发起公开申请。
11. 生成失败时，用户看到可理解错误原因和是否扣费；未生成任何图片不得扣费。

### 6.2 登录会话续期流程

1. 用户访问已登录页面时，前端携带 Access Token 请求接口。
2. 若 Access Token 过期但 Refresh Token 未过期，客户端无感发起续期请求。
3. 服务端校验 Refresh Token 成功后，同时返回新的 Access Token 和 Refresh Token。
4. 客户端更新本地会话并重放原请求，用户留在原页面继续操作。
5. 若两个 Token 都失效或续期失败，客户端记录当前目标页面地址并跳转登录页。
6. 用户重新登录成功后，自动跳转回失效前的原页面。

### 6.3 API Key 调用流程

1. 用户进入密钥管理页，点击创建密钥。
2. 用户填写密钥名称、分组、额度上限、过期时间和 RPM 限速。
3. 系统生成 Access Key 和 Secret Key；Secret 仅创建时展示一次。
4. 开发者使用 AK/SK 调用统一生成 API，可提交文生图、图生图或参考图生成任务。
5. 系统按密钥、用户账号和平台策略进行鉴权、限速、额度校验。
6. 请求成功创建任务后返回任务 ID；同步接口可直接返回图片结果，异步接口返回查询地址。
7. 开发者通过任务查询接口获取状态、图片 URL、积分消耗和错误码。

### 6.4 管理后台运营流程

1. 超级管理员登录独立后台。
2. 在模型接入页维护底层模型供应商、模型名称、成本口径、可用状态和健康状态。
3. 在抽象模型分组页将底层模型归入 Basic/Plus/Pro 或自定义分组。
4. 配置每个分组的优先级、AB 分流比例、失败降级链路和任务类型可用参数范围。
5. 在积分策略页配置按分组、质量、任务类型、数量计算的积分消耗。
6. 在系统配置中心通过分类 Tab 管理认证安全、生成参数上限、数量上限、公开审核开关、运营活动等配置。
7. 在兑换码页生成兑换码，设置面额、有效期、使用次数和适用用户范围。
8. 在用户管理页处理禁用、重置密码、积分调整、并发和 RPM 设置。
9. P1 阶段在公开图片审核页处理待审核图片的通过、拒绝和下架。
10. 在调用记录和监控大盘查看成功率、失败原因、用户消耗、底层成本和毛利估算。

## 7. 系统行为流程

### 7.1 图片生成请求处理

```text
用户/API 请求 -> 解析输出图片数量与参考图片数量 -> 解析质量档位/auto 分辨率 -> 参数校验 -> 登录/密钥鉴权 -> 用户状态校验 -> 限速校验 -> 余额/套餐校验 -> 预计积分计算 -> 创建任务与预扣/锁定积分 -> 模型分组路由 -> 调用底层模型 -> 保存图片与元数据 -> 实际扣费/返还 -> 返回结果 -> 写审计与统计
```

### 7.2 模型路由规则

1. 用户选择的是抽象模型分组，不直接选择底层供应商模型；管理后台可决定该分组包含哪些底层模型。
2. 分组内模型按启用状态、任务类型兼容性、参数兼容性、健康状态、优先级和 AB 分流比例决定候选顺序。
3. 底层模型失败时，若错误属于可降级类型，则按降级链路尝试下一模型；不可降级类型直接失败。
4. 降级不得突破用户选择的抽象模型等级；例如 Basic 不得自动升级到 Pro 并增加用户扣费。
5. 若降级后实际成本高于预计成本，用户积分仍按提交时展示的计费规则扣除，成本差由平台承担。
6. 图生图和参考图生成任务必须优先匹配明确支持图片输入的底层模型；若当前分组没有兼容模型，应在提交前阻止用户发起请求。

### 7.3 计费规则

- 积分与人民币的默认汇率为 `1 积分 = 0.3125 元`，等价于 `1 元 = 3.2 积分`；后台可调整该汇率。
- 平台内积分支持小数计算，**最大支持到小数点后 5 位**；所有计费、预扣、返还、流水和余额都按 5 位小数精度处理。
- 用户提交前必须展示预计消耗；预计消耗、实际消耗和返还积分都使用统一公式计算。
- 单张基础积分由抽象模型分组和实际结算分辨率档位共同决定，默认策略如下：

| 抽象模型 | 1K | 2K | 4K | 适用说明 |
|---|---:|---:|---:|---|
| Basic | 2 | 4 | 8 | 低成本、速度优先、适合草稿 |
| Plus | 5 | 8 | 16 | 质量和成本均衡，默认推荐 |
| Pro | 后台配置 | 后台配置 | 后台配置 | 高质量优先，前端展示后台当前策略 |

- 平台需支持用户分组倍率。每个用户至少归属一个用户分组，默认分组倍率为 `1.00000`；后台可为不同用户分组配置倍率，例如首充用户、渠道用户、VIP 用户、测试用户等。
- 平台需区分“输出图片数量”和“参考图片数量”：
  - **输出图片数量**：本次任务最终希望生成多少张结果图。Web 端读取数量选择器；OpenAI 兼容接口和平台原生 API 读取 `n` 或等价字段；缺省值为 `1`。
  - **参考图片数量**：本次请求作为输入上传或关联的参考图数量，仅图生图/参考图生成/编辑类任务使用；缺省值为 `0`。
- 图片数量默认 1，前台可选范围为 `1-5`；运营后台可配置最大生成数量，默认上限为 5，前台实际可选上限取后台配置值。
- 图生图与参考图生成的价格必须与文生图区分：
  - 文生图默认任务类型倍率为 `1.00000`
  - 二次编辑（图生图）默认任务类型倍率为 `1.25000`
  - 参考图生成默认任务类型倍率为 `1.15000`
  - 当请求中包含参考图时，默认启用参考图附加倍率：第 1 张参考图默认 `+0.10000`，从第 2 张开始每增加 1 张参考图默认再增加 `+0.05000`
  - 上述倍率均可由后台调整
- 平台需支持 `auto` 分辨率/质量档位，并明确实际结算档位的判定逻辑：
  1. 若用户显式选择 `1K/2K/4K`，按显式档位结算。
  2. 若请求携带显式尺寸（如 OpenAI 兼容接口的 `size`、平台原生接口的 `width/height`），则按**最长边**落桶：最长边 `<=1024` 记为 `1K`，`1025-2048` 记为 `2K`，`2049-4096` 记为 `4K`；超过平台允许最大尺寸则直接拒绝。
  3. 若请求为 `auto` 且没有显式尺寸，则按抽象模型分组默认档位结算：Basic 默认 `1K`、Plus 默认 `2K`、Pro 默认 `4K`；后台可改每个分组的 auto 默认档位。
  4. 若用户只选择比例、未选择尺寸，则系统先按 auto 规则确定档位，再将比例映射到该档位下的具体宽高。
- **完整费用伪公式**如下：

```text
ResolvedQualityBucket =
  if explicit_quality in {1K,2K,4K} then explicit_quality
  else if explicit_size exists then bucket_by_longest_edge(explicit_size)
  else default_quality_by_model_group(selected_model_group)

BaseUnitPoints = PriceTable(selected_model_group, ResolvedQualityBucket)

TaskTypeMultiplier =
  case task_type of
    text_to_image => 1.00000
    image_edit => 1.25000
    reference_generate => 1.15000
    else => backend_config

ReferenceImageExtraMultiplier =
  if reference_image_count == 0 then 0
  else 0.10000 + max(reference_image_count - 1, 0) * 0.05000

UserGroupMultiplier = current_user_group.multiplier

EstimatedPoints =
  round_5(
    BaseUnitPoints
    * requested_output_image_count
    * TaskTypeMultiplier
    * (1 + ReferenceImageExtraMultiplier)
    * UserGroupMultiplier
  )

ActualPoints =
  round_5(
    BaseUnitPoints
    * success_output_image_count
    * TaskTypeMultiplier
    * (1 + ReferenceImageExtraMultiplier)
    * UserGroupMultiplier
  )
```

- 总消耗按 `ActualPoints` 结算。
- 任务全部失败不扣积分；多图部分成功仅扣成功图片积分。
- 如果系统采用预扣，失败或部分失败必须生成返还流水。
- 套餐额度优先于通用余额消耗；活动赠送积分优先级低于套餐额度，高于充值余额。后台可调整消耗顺序，但前端必须展示当前规则。
- 管理员手动扣减积分必须填写原因，且用户可在流水中看到“管理员调整”类型，但默认不展示后台操作人姓名。

## 9. 异常场景与边界条件

| 场景 | 产品行为 | 是否扣费 |
|---|---|---|
| 未登录访问生成页 | 引导登录 | 不扣费 |
| Access Token 过期但 Refresh Token 有效 | 静默续期并重放原请求 | 不额外扣费 |
| Access Token 和 Refresh Token 都失效 | 跳转登录页，登录后回原页面 | 不额外扣费 |
| 余额不足 | 禁用提交并展示充值/兑换入口 | 不扣费 |
| Prompt 为空或超长 | 表单内提示具体限制 | 不扣费 |
| 图生图/参考图缺少参考图片 | 阻止提交并提示上传图片 | 不扣费 |
| 图生图/参考图参考图片数量超限 | 阻止提交并提示当前模型或平台支持的最大参考图数量 | 不扣费 |
| 参考图片格式或大小不合法 | 阻止提交并提示限制条件 | 不扣费 |
| 请求质量为 `auto` | 系统按第 7.3 节规则解析实际结算档位，并在任务详情中展示解析结果 | 按解析后的档位结算 |
| OpenAI 兼容接口未显式传 `n` | 默认按 1 张输出图片处理 | 按 1 张结算 |
| 选择参数无可用模型支持 | 提示调整参数，提交按钮不可用 | 不扣费 |
| 用户被禁用 | 登录态失效或 API 返回账号禁用 | 不扣费 |
| API Key 禁用/过期/删除 | API 返回鉴权失败错误码 | 不扣费 |
| 超过 RPM 或并发 | 返回限速提示和重试建议 | 不扣费 |
| 底层模型超时 | 尝试可用降级；全失败则任务失败 | 全失败不扣费，部分成功按成功数扣费 |
| 底层模型返回原始错误码或内部错误体 | 平台先归一化判断是否重试、包装或屏蔽，普通用户默认不直接看到上游原始错误内容 | 按最终任务状态扣费 |
| 图床保存失败 | 任务失败或部分失败；不得只扣费不展示图片 | 未保存成功的图片不扣费 |
| 多图部分失败 | 展示成功图片和失败数量/原因 | 仅成功图片扣费 |
| 用户删除历史图片 | 图库不可见，流水保留 | 不产生退款 |
| 管理员修改价格时用户正在生成 | 已提交任务按提交时价格扣费 | 不追加扣费 |
| 后台将最大生成数量下调 | 新页面配置即时生效；旧草稿提交时重新校验 | 超限则阻止提交，不扣费 |
| 兑换码并发使用 | 只有一个请求可核销成功 | 成功请求入账，失败请求提示已核销/次数超限 |
| 支付成功但前端关闭 | 后台订单状态最终入账，用户刷新后可见 | 以支付结果为准 |
| 网络中断 | Web 端可在历史任务中继续查看状态 | 按最终任务状态扣费 |
| 公开审核被拒绝 | 图片保持私有，用户可见拒绝原因 | 不涉及扣费 |
| 已公开图片被下架 | 从广场中移除，用户在历史中可见下架状态 | 不涉及扣费 |

## 11. 安全与合规要求

- 密码、Secret Key、底层模型密钥不得明文存储；Secret 仅创建或重置时展示一次。
- 客户端用户只能访问自己的图片、任务、密钥和流水；所有资源接口必须校验归属。
- 管理后台与客户端账号体系隔离；后台登录需要更高强度密码策略，预留二次验证能力。
- Access Token 有效期 10 分钟，Refresh Token 有效期 2 小时；静默续期成功时必须轮换两者，避免长期复用旧 Token。
- 当双 Token 失效时，必须跳转登录页并在重新登录后回到原页面，避免用户在受保护页面看到无权限空白态。
- 管理员调整积分、导出兑换码、修改模型密钥、修改价格策略、禁用用户、下架公开图片等高风险动作必须二次确认并审计。
- 不允许普通用户通过错误信息看到底层供应商密钥、内部模型账号、成本配置或其他用户信息。
- 上游模型供应商的错误信息必须先经过平台归一化处理：不是所有原始错误码都直接透出，普通用户默认只看到平台标准错误码和可理解文案。
- Prompt、参考图和生成结果可能包含敏感内容，本期至少保留内容安全策略开关；P1 公开图片流程必须经过人工审核后才能对外展示。
- 用户删除图片后，前端不可再访问该图片 URL；后端可按存储清理策略异步删除文件。
- 支付、退款、订阅等资金相关动作必须保留订单状态、金额、渠道流水号和操作记录。

## 15. 兼容性影响

- 空仓库新项目，不涉及存量用户数据迁移。
- 由于本期会定义积分、任务、图片、公开状态和模型配置核心数据结构，后续新增社区互动、团队空间时需要兼容已有任务和流水。
- 底层模型参数差异通过抽象模型和参数能力配置消化；用户端不得直接依赖某一底层模型的私有参数。
- 价格策略变更只影响新任务；历史任务、流水和用户已展示的任务价格不回溯重算。
- API Key Secret 重置后旧 Secret 立即失效，开发者需要主动更新调用方配置。
- Web Token 续期策略变化时，不应影响已登录用户的原页面回跳逻辑。

## 16. 灰度计划

| 阶段 | 范围 | 周期 | 进入下一阶段条件 | 回退条件 |

| Beta 小范围 | 100-500 个用户，开放兑换码入账 | 2 周 | 成功率 >= 95%，P95 任务完成时间符合所选模型预期，积分流水准确率 100% | 成功率低于 90% 持续 2 小时，或出现资金/积分异常 |
| 公测 | 开放注册，限制并发和日额度 | 2-4 周 | 支付/兑换/模型路由稳定，客服问题可控 | 关键模型不可用且无降级、图片存储异常、严重安全问题 |
| P1 分享灰度 | 小范围开放公开申请和图片广场 | 1-2 周 | 审核时效、下架流程、公开内容质量可控 | 审核积压、违规内容外露、广场性能异常 |
| 全量 | 取消白名单限制 | 持续运营 | 监控大盘和审计可支撑运营 | 按模块关闭生成、支付或公开入口 |

## 17. 性能与体验要求

| 场景 | 要求 |
|---|---|
| 前端页面首屏 | 常规网络下客户端首页和生成页首屏加载 P75 <= 2.5 秒 |
| 表单反馈 | 参数变更后预计积分 300 ms 内更新 |
| Token 静默续期 | 正常情况下 1 秒内完成续期并重放原请求，用户无感知 |

| 异步任务查询 | Web 轮询间隔默认 2-5 秒，失败后退避；API 查询返回 P95 <= 500 ms（不含底层模型生成时间） |

## 18. 多语言要求

- 客户端和管理后台文案需支持中文、英文资源文件结构。
- MVP 默认中文；英文翻译至少覆盖登录注册、文生图、图生图、历史、密钥、余额、常见错误提示和后台核心菜单。
- P1 阶段图片广场、公开审核状态和审核结果提示也需覆盖中英文。
- 用户生成的 prompt、昵称、签名不做自动翻译。
- 错误码保持稳定，错误文案按语言资源展示。

## 24. 优先级依据

- 需求整体标为 P0，因为没有用户、会话安全、积分、图片生成、模型路由和管理后台闭环，就无法验证产品商业模式。
- P0 子功能限于“完成可运营的生图闭环”的必要能力；双 Token 续期、文生图、图生图、参考图生成、OpenAI 兼容接口、开发文档页面、配置中心属于 P0。
- P1 子功能是公开图片审核和图片广场，因为它们属于用户分享与内容运营能力，不影响首阶段生图和计费主闭环。
- 支付自动化为 P1，但充值/兑换/管理员入账和订单状态闭环为 P0，因为内测可先用兑换码或手动入账替代真实支付。
- 多语言为 P1，但文案资源结构为 P0，以避免后续重构。

## 25. 研发关注点（产品层面需评审确认）

1. 抽象模型分组名称是否固定为 Basic/Plus/Pro，还是后台允许运营自定义展示名并影响前端筛选。
2. Pro 分组默认积分暂不在 PRD 固化，是否接受由后台首版配置后在上线前确认展示策略。
3. MVP 内测阶段是否允许只接入 1 个底层模型；若只有 1 个模型，则降级策略无法完整验证。
4. 图生图和参考图生成对参考图大小、格式、参考强度、最大参考图数量的真实支持范围，需要在技术方案阶段与底层模型能力对齐。
5. 支付自动化是否进入公测前必需范围；如果延期，公测是否仅通过兑换码和管理员手动充值运营。
6. 公开图片审核的时效 SLA、拒绝原因模板和下架标准，需要在 P1 阶段进一步产品化。
7. API 的同步等待超时时间、异步任务保留时间和静默续期失败后的兜底策略，需在技术方案阶段给出默认值。
8. OpenAI 兼容接口与平台原生接口在字段能力上可能存在差异，哪些差异允许通过开发文档说明解决，哪些必须在接口行为上完全兼容，需要技术方案阶段逐项落表。
9. 上游错误码归一化的策略边界、自动重试条件、可直出条件和屏蔽条件，需要在技术方案阶段按 OpenAI 和 OpenRouter 官方文档形成明确规则。
