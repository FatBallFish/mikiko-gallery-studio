## 产品实现逻辑提炼

### 需求一句话摘要

建设一个同时支持文生图、图生图、参考图生成的图片生成平台，在底层图像模型 API 之上提供双 Token 登录态、积分计费、私有图库、统一 API Key、模型路由、配置中心和后续公开图片广场能力。

### 范围边界

- **In-scope（本期做）**：
  1. 【事实】用户注册登录、双 Token 会话管理、个人资料、额度、兑换/订阅入口和密钥管理（PRD 第 3.1、8.1-8.4 节）。
  2. 【事实】文生图、图生图、参考图生成、同步/异步、生图历史和私有图库（PRD 第 3.1、6.1、8.5-8.6 节）。
  3. 【事实】积分计费、模型接入、任务类型倍率、优先级、AB 分流、降级、配置中心和调用记录（PRD 第 3.1、7、8.8-8.9 节）。
  4. 【事实】公开图片申请、人工审核和图片广场作为 P1 已纳入整体范围（PRD 第 3.1、5.6、8.6-8.9 节）。
  5. 【事实】安全合规、审计、开放 API、灰度、性能、多语言和 Docker 交付要求（PRD 第 11-23 节）。
- **Out-of-scope（本期不做）**：
  1. 【事实】视频生成、自研模型训练、原生 App、完整第三方登录、复杂组织空间和公开社区互动（PRD 第 3.2 节）。

### 用户操作流程

1. 【事实】用户登录成功后获得 Access Token 和 Refresh Token，并进入图片生成页（PRD 第 6.1、6.2 节）。
2. 【事实】用户可选择文生图、二次编辑或参考图生成；后二者需要上传参考图片（PRD 第 6.1、8.5 节）。
3. 【事实】系统展示预计积分消耗，校验余额、限速和参数后创建任务（PRD 第 6.1、7.1、7.3 节）。
4. 【事实】任务成功后进入历史图库，用户可预览、下载、删除；P1 阶段可申请公开（PRD 第 6.1、8.6 节）。
5. 【事实】开发者可通过 AK/SK 调用统一接口并查询任务状态（PRD 第 6.3、13 节）。
6. 【事实】管理员维护模型、积分策略、系统配置，并在 P1 阶段处理公开审核（PRD 第 6.4、8.8-8.9 节）。

### 系统行为流程

1. 【事实】请求经参数校验、登录/密钥鉴权、用户状态校验、限速、余额校验、积分预估、任务创建、模型路由、结果保存和计费返还（PRD 第 7.1 节）。
2. 【事实】模型路由按任务类型兼容性、参数兼容性、优先级、AB 分流和降级链路执行（PRD 第 7.2 节）。
3. 【事实】当 Access Token 失效但 Refresh Token 有效时，系统会静默续期并重放原请求（PRD 第 6.2、8.1 节）。
4. 【事实】公开图片要经过待审核池和人工审核后才能进入广场（PRD 第 8.6-8.9、10.1 节）。

### 核心规则/策略逻辑

- 【事实】用户选择抽象模型分组而不是底层供应商；后台决定分组内模型和可用任务类型（PRD 第 7.2、8.8 节）。
- 【事实】Basic 和 Plus 的默认积分已固定，Pro 默认积分由后台首版配置（PRD 第 7.3 节）。
- 【事实】图片数量默认 1，可选 1-5，真实上限取后台配置（PRD 第 7.3、8.5 节）。
- 【事实】图生图和参考图生成默认复用基础积分，并支持后台倍率配置（PRD 第 7.3、8.8 节）。
- 【事实】双 Token 失效时必须跳转登录，重新登录后回原页面（PRD 第 6.2、8.1 节）。
- 【事实】公开图片只有审核通过后才能在广场展示（PRD 第 5.6、8.6-8.7 节）。

### 数据流向

```text
用户输入/上传参考图 -> Pic Gallery 后端校验与任务记录 -> 底层模型 API -> 图片文件/URL -> 平台图床与历史图库 -> 用户前端/API 返回
后台配置 -> 模型分组/价格/路由策略/数量上限/审核开关 -> 新生成任务读取配置 -> 调用记录与成本统计 -> 管理后台大盘
支付/兑换/管理员调整 -> 积分流水 -> 用户额度视图 -> 生成前余额校验
用户申请公开 -> 待审核图片池 -> 管理员审核 -> 图片广场瀑布流
登录成功/续期 -> Access Token + Refresh Token -> Web 端受保护页面访问
```

### 提炼过程中发现的疑问

**PRD 应回答的（产品行为/业务规则）：**
1. Pro 分组默认积分是否需要在上线前固定到发布清单中，而不是继续只放在后台配置中（PRD 第 7.3、25 节）。
2. P1 公开审核的 SLA、拒绝原因模板和下架标准需要在开启前细化（PRD 第 8.9、16、25 节）。

**技术方案阶段回答的（实现机制，不算 PRD 缺陷）：**
1. 双 Token 续期接口、刷新令牌轮换、原请求重放和回跳实现。
2. 图生图/参考图生成与底层模型能力矩阵的映射和参数降级策略。
3. 对象存储私有访问、公开内容展示链路和删除/下架后的缓存清理。
4. 积分预扣/返还幂等、公开审核操作审计和支付回调一致性。

### 必须项深度分析

#### 1. 需求背景与目标

PRD 第 1 节明确说明了为什么要在 MVP 阶段纳入图生图/参考图生成，以及为什么会话安全和配置中心属于主闭环。其“图生图、参考图生成和二次编辑已经是高频需求，如果 MVP 阶段只支持文生图，平台在真实场景中的可用性会明显不足”直接解释了本轮修改的紧迫性；“如果不在 MVP 阶段建立积分、会话安全、审计和历史数据闭环”解释了不做的后果。目标表同时给出生成闭环、续期体验、配置生效和分享能力的量化口径。

#### 2. 用户故事 JTBD 分析

- C 端用户：情境从纯文本扩展到已有图片编辑；Job 是低学习成本完成文字到图片或图片到图片的转换；替代方案是直接使用底层模型。故事成立。
- API 开发者：情境是业务应用集成多种生成任务；Job 是统一接口、可计费、可查询地调用图片生成。故事成立。
- 运营管理员：情境是动态调价、调路由、调上限和开关；Job 是配置驱动运营。故事成立。
- 图片分享用户：情境是想展示作品；Job 是不影响私有图库的前提下公开单张作品；这与 P1 图片广场能力对应，故事成立。

#### 3. 功能范围与产品设计闭环

PRD 已形成从注册登录、会话续期、积分、三类生成任务、历史图库、API Key、后台模型与积分策略、系统配置中心，到 P1 公开审核/图片广场的完整闭环。Out-of-scope 清楚排除了公开视频、原生 App、社区互动等范围膨胀项。关键冲突规则已处理：如“Pro 默认积分后台配置”“公开内容先审后发”“后台调低数量上限后超限提交需重新校验”“双 Token 失效后回原页面”。

#### 4. 验收标准质量

验收标准可直接落到测试：例如 Access 10 分钟、Refresh 2 小时、静默续期、参考图缺失报错、数量默认 1 且可选 1-5、Basic/Plus 默认积分矩阵、后台数量上限动态生效、公开审核状态流转等。正常链路、异常链路和 P1 后置能力均有覆盖。

#### 6. 优先级合理性

PRD 第 24 节明确将图生图、参考图生成、双 Token 续期和配置中心归为 P0，这是合理的，因为它们直接影响平台是否可用于真实生成场景。公开审核和图片广场被降为 P1，也符合“先做生成与计费主闭环，再做内容运营”的节奏。P0/P1 边界清楚，没有出现 P0 通胀。

## 研发关注点

1. 图生图和参考图生成进入 P0 后，底层模型能力矩阵必须优先明确，否则前端参数和路由策略会反复调整。
