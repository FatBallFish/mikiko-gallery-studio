## 二、方案复述还原

### 一句话摘要

方案准备基于 Go 单体服务搭建一个图片生成平台，把 Web 用户、AK/SK 开发者、管理后台都统一接入“任务先落库、再由执行器调度上游模型”的链路，并用 PostgreSQL、Redis、对象存储承载状态、缓存和文件。

### 核心架构决策

1. 任务执行不走纯同步转发，而走统一任务编排模型。
2. Web 会话不走纯 JWT，而走短 Access JWT + 轮换 Refresh Session。
3. 文件存储不写死某一家云存储，而采用 Local FS / S3 兼容双驱动。
4. 运营侧大量规则不写死代码，而放入带分类 Tab 的配置中心。
5. P1 公开广场先预埋状态机与审核数据模型，但通过功能开关默认关闭。

### 系统交互全景

- Web Client / Admin Web / Open API 请求进入统一 API 网关。
- 登录、余额、任务、配置等核心能力均落在单体后端内部模块。
- 图片生成先写任务与预扣流水，再由 Worker 调用 provider，最后写图片、结算积分与审计。
- 参考图和结果图走对象存储；验证码、限流、热会话和配置热点走 Redis。
- 管理后台通过配置中心控制路由、定价、数量上限和公开开关。

### 方案边界

- **In-scope**：登录注册、双 Token、文生图、图生图、参考图、API Key、计费、模型路由、配置中心、后台管理。
- **Out-of-scope**：视频生成、原生 App、自研模型、复杂社区互动。
- **外部依赖**：图片 provider、对象存储、SMTP、支付渠道。

### 复述中发现的疑问

1. 【缺失】方案已设计 `reference_image_ids`，但没有补齐“参考图如何上传并变成可复用 image id”的完整接口链路。
2. 【缺失】方案采用 Access in-memory + Refresh Cookie，但没有明确页面刷新、浏览器重启后如何恢复登录态以及如何保存原页面回跳信息。

## 三、全局架构审视

### 问题域与业界做法

- 多 provider 图片平台通常不会把图生图当成文生图附属字段，而会抽象成独立任务类型与能力矩阵。
- Web 双 Token 会话主流做法是短 Access + 轮换 Refresh，避免长期暴露 refresh token。
- 对象存储通常需要直传/中转双模式，以同时兼容首版实现成本和后续规模化。

### 方案整体评估

- 大方向合理，没有明显过度设计：
  - 没有在空仓库阶段就拆微服务。
  - 没有为了“简单”回退成纯同步转发。
  - 计费、历史、审核、模型路由、配置快照都围绕任务模型统一起来了。
- 主要问题不在总体架构，而在两条关键子链路没有闭环：
  1. 图生图/参考图的“上传 -> 校验 -> 生成时引用”链路缺口。
  2. 双 Token 的“页面刷新/回跳/单飞刷新”前端行为没有明确落地。

### 全局判定

🟢 方向正确，但需先补完以下关键链路再准出：

1. 参考图资产上传闭环。
2. Web 会话恢复与原页面回跳闭环。

## 四、关键问题

### [重要] 缺少参考图上传与复用的完整资产链路

- 位置：`/Users/fatballfish/Documents/Projects/GoProjects/Personal/pic-gallery/docs/tech/pic-gallery-tech-design.md` §2.4、§2.6
- 问题：
  - 方案中的创建任务接口依赖 `reference_image_ids`。
  - 但当前接口清单里没有给 Web 用户或 AK/SK 开发者提供“上传参考图、拿到 image_id/object_key、再提交任务”的标准入口。
  - 如果不补这个链路，图生图/参考图生成在接口层面是不可用的。
- 影响：
  - 直接阻塞 PRD A7、A9、A11 中与图生图/参考图相关的验收。
  - 也会影响后续对象存储清理、权限归属和内容安全校验。
- 建议：
  - 增加独立的参考图上传接口族，至少覆盖：
    - Agent API：前端上传参考图、查询上传结果、删除未使用临时参考图。
    - Open API：开发者上传参考图或创建预签名上传会话。
    - Inner API：直传完成确认。
  - 数据模型中区分“临时参考图资产”和“任务输出图”，并定义未引用超时清理策略。

### [重要] 双 Token 方案缺少页面刷新恢复、回跳保存与单飞刷新约束

- 位置：`/Users/fatballfish/Documents/Projects/GoProjects/Personal/pic-gallery/docs/tech/pic-gallery-tech-design.md` §2.2、§2.3、§2.4
- 问题：
  - 当前方案说明了 Access Token 在内存、Refresh Token 在 Cookie，也说明了静默刷新。
  - 但没有明确：
    1. 浏览器刷新页面后如何恢复 Access Token；
    2. 多个并发请求同时 401 时如何避免刷新风暴；
    3. 双 Token 都失效时，原目标页面地址如何保存并在重新登录后恢复。
- 影响：
  - 这会让 PRD 明确要求的“无感续期”和“登录后回原页面”在实现细节上存在歧义。
  - 前后端联调时容易出现重复请求、页面闪退到登录页、返回首页而不是原页面等体验问题。
- 建议：
  - 在方案里明确前端会话状态机：
    - App 初始化时若无 Access Token 但存在 Refresh Cookie，先触发 bootstrap refresh。
    - 刷新请求采用 browser-tab 级 singleflight。
    - 当 refresh 失败时，把 `return_to` 写入 sessionStorage，再跳登录页；登录成功优先跳回 `return_to`。
  - 增加一个简要时序或伪代码，约束 Web 端标准实现。
